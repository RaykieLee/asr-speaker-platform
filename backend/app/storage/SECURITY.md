# 存储加密与部署验收

转写音频、注册声纹样本、声纹 embedding、任务结果和 SQLite 数据库均可能包含敏感信息。**Unix 文件权限只能限制本机账户访问，不会加密磁盘、数据库或备份。**本工具会分别检查权限和静态加密状态；所有检查都通过才返回退出码 0。遇到不支持的平台、缺少命令、无法确认卷归属或加密状态时会失败关闭。输出仅包含检查名称、状态和通用原因码，不打印路径、卷名、设备名或数据内容。

## 运行检查

从仓库根目录运行；数据目录默认读取 `ASR_DATA_DIR`，否则为 `data/`。至少指定一个已存在的备份目录，可重复传入以覆盖每个备份位置：

```sh
python3 scripts/storage_security_check.py \
  --data-dir "${ASR_DATA_DIR:-data}" \
  --backup-dir /secure-backups/asr
```

检查数据目录、SQLite 主库以及存在时的 `-wal`/`-shm` 文件、录音文件树和备份文件树均不允许组或其他账户访问；发现符号链接、无法读取权限或缺少必需目录也会失败。WAL/SHM 文件在 SQLite 未运行或已检查点清理时可以不存在。目录树会逐项检查现存文件和目录，因此在大型音频归档上运行可能需要时间。

在 macOS 上，脚本实际运行 `fdesetup status` 确认 FileVault 为 On，并对数据卷和每个备份卷分别查询 `diskutil info -plist`，要求卷报告加密且路径确实位于该挂载点内。FileVault 开启只保护其覆盖的卷；外置备份盘仍需单独确认卷加密。

在 Linux 上，每个数据/备份路径都必须由 `findmnt` 映射到 `/dev/mapper/<name>`，并由 `cryptsetup status <name>` 明确报告活动的 LUKS1/2 映射及底层块设备。普通 ext4/XFS 挂载、容器 overlay、云盘加密声明或只加密备份软件输出都无法由本脚本证明，因此会失败关闭。部署方应使用发行版支持的 LUKS2 全盘/数据卷配置，将数据目录和备份目录实际放在对应解锁后的 mapper 卷上，并在启动 ASR 服务前挂载、解锁和运行此检查。可人工复核：

```sh
findmnt --target /srv/asr-data
sudo cryptsetup status asrdata
```

不要对已有卷直接执行格式化或初始化命令；先由部署管理员制定迁移和恢复方案，并验证加密卷之外的备份副本。

## 密钥和备份责任

应用只写 SQLite 和文件，不创建或托管磁盘加密密钥。部署方负责选择加密卷、设备与备份系统，安全保管恢复密钥（独立于被加密设备和备份），控制谁能解锁、轮换/撤销密钥，并定期做断电恢复演练。在线数据库备份会复制应用数据；请将其直接写入加密备份卷或加密备份系统，不能先落到未加密临时目录再搬运。密钥丢失会令加密数据不可恢复。

`backend/app/storage/README.md` 的 `700`/`600` 权限建议是纵深防护，不代替 FileVault、LUKS 或备份系统加密。本脚本不检查 ACL、云提供商的静态加密、密钥保管策略、硬件安全模块、卷是否在远端备份中加密，也不能防御已有本机管理员权限的攻击者；这些需由运维策略和基础设施配置另行验收。
